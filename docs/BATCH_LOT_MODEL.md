# Batch / lot model (Phase A5-B)

A **lot** is a quantity of one product that arrived at one node in one event
(normally one goods-receipt line) and can be followed from supplier to
customer. In DG Way the lot is a **dimension of the inventory ledger**, not a
second stock system: `stock_movements` stays the only source of truth, every
movement simply names the lot it moved.

```
supplier ──GR line──▶ LOT ──movements (lot_id)──▶ sale lines ──▶ customers
                       │                      └─▶ losses, returns, regrades (derived lots)
                       └─ provenance: supplier, GR, GR line, dispositions, dates
```

## 1. Identity

| Field | Rule |
| --- | --- |
| `id` | UUIDv7, generated by the server, never changes, never reused |
| `number` | `LOT-YYMMDD-NNN`, issued by the server from the `LOT` document sequence of the lot's business date (same generator as SAL/PO/GR). Clients never send it. Unique, immutable |
| `origin` | `RECEIPT`, `REGRADE`, `ADJUSTMENT`, `LEGACY` (see §2) |
| `product_id`, `node_id`, `uom_code` | fixed for life; movements of another product/UOM cannot use the lot (trigger `dgway_movement_lot_guard`) |
| `original_quantity` | quantity that CREATED the lot (NULL only for LEGACY: unknown) |
| `supplier_id`, `goods_receipt_id`, `goods_receipt_line_id` | provenance (RECEIPT; REGRADE copies the root supplier) |
| `parent_lot_id` | lineage (REGRADE only) |
| `source_document_type/id` | the document that created the lot |
| `business_date`, `received_at` | FIFO keys (Asia/Jakarta business date; UTC instant) |
| `manufactured_date`, `best_before_date` | optional, only if the operator typed them on the receipt line; never invented |

`inventory_lots` is **append-only** (`inventory_lots_append_only`: no UPDATE,
no DELETE). A lot is never edited; corrections are movements (reversal,
adjustment, regrade) that are themselves recorded against lots.

**Status is derived, not stored**: `ACTIVE` while any bucket of the lot holds
stock, `DEPLETED` when all buckets are zero. There is no status column to
drift. (Expired/blocked statuses are intentionally not modelled: no FEFO,
no expiry policy has been approved.)

## 2. Creation

| Origin | Created by | Quantity | Provenance |
| --- | --- | --- | --- |
| `RECEIPT` | posting a goods receipt: **one lot per receipt line** (`lot_one_per_receipt_line`) | received quantity of the line | supplier, GR, GR line (DB-checked: `dgway_lot_guard` compares product, supplier, node, uom with the GR line) |
| `REGRADE` | a REGRADE disposition at receiving, or a regrade inventory operation | regraded quantity | `parent_lot_id`; supplier + dates copied from the parent; one derived lot per parent × source document × target product (`lot_one_derived_per_source`) |
| `ADJUSTMENT` | stock-count adjustment IN (stock appears with no known origin) | adjusted quantity | none (no supplier) — honest "found stock" |
| `LEGACY` | the A5-B migration, once per product × node that had stock history | NULL (unknown) | none — **unattributed legacy provenance**, no supplier/GR is invented |

Lots are created inside the same transaction as the posting, so a failed or
retried posting leaves no lot and burns no lot number (LOT sequence rolls back
with it). A retried request with the same Idempotency-Key replays the original
response; a new key on an already posted receipt gets 409 and no lot.

Deferred trigger `dgway_check_lot_origin_quantity` enforces at COMMIT:
Σ quantity of the lot's creating movements (RECEIPT / REGRADE_IN /
ADJUSTMENT_IN) = `original_quantity`. A creating movement can only target a
lot of the matching origin created by the same source document.

## 3. Dispositions at receiving

Example from the brief — 150 kg received, 140 ACCEPT, 10 LOSS:

| Movement | Bucket | Lot | Qty |
| --- | --- | --- | --- |
| RECEIPT | AVAILABLE | LOT-A | +140 |
| RECEIPT | QUARANTINE | LOT-A | +10 |
| LOSS | QUARANTINE | LOT-A | −10 |

Lot A: original 150 (= 140 + 10 created), remaining 140 AVAILABLE. The loss is
part of the lot's history (traceable to the GR and the reason). RETURN_TO_SUPPLIER
goes to RETURN_PENDING in the same lot. REGRADE moves the regraded part to a
derived lot of the target product (REGRADE_OUT from LOT-A, REGRADE_IN into the child).

## 4. FIFO

Allocation is **server-side** and **FIFO** within one position
(product × node × bucket): oldest `business_date`, then `received_at`, then
lot `number`. The client never chooses or sends a lot.

FEFO (first-expired-first-out) is **not** implemented: best-before dates are
optional and incomplete, so ordering by them would be fake FEFO. FIFO is
documented and deterministic; FEFO can be added later as another allocation
policy when dates are mandatory for a product category.

Used by: sales, losses, supplier returns, adjustments OUT, regrade operations,
recoveries (which keep the lot and move it between buckets).

## 5. Sale allocation

Confirming a sale (A4 `ConfirmSale`) now produces **one SALE movement per sale
line per lot**: a 30 kg line served by LOT-A (20) and LOT-B (10) gives two SALE
movements with the same `source_line_id`. Customer destination = sale →
customer, joined from the movement's `source_document_id`/`source_line_id`.

## 6. Returns (deterministic policy)

A customer return must put stock back into the lot(s) the customer actually
received. Policy:

> The returned quantity of a sale line is attributed to that line's lots **in
> allocation order** (oldest consumed lot first), each lot up to
> `consumed − already returned`.

It is derived from the ledger (`SaleLotConsumption`: non-reversed SALE
movements minus earlier CUSTOMER_RETURN movements of the line), so it is the
same on every retry and after any number of partial returns. The return's
disposition decides the bucket (RETURN_TO_AVAILABLE → AVAILABLE;
RETURN_TO_QUARANTINE → QUARANTINE; LOSS → into QUARANTINE and written off) —
always in the original lot.

## 7. Reversals

A REVERSAL mirrors its original movement exactly, **including the lot**
(`dgway_validate_reversal` checks it). Reversing a pre-A5-B movement
(lot_id NULL) uses the LEGACY lot of its product/node.

## 8. Remaining quantity

```
remaining(lot, bucket) = Σ signed_quantity of movements of that lot in that bucket
```

`stock_lot_balances` (lot × node × bucket) is a projection maintained in the
same transaction as `stock_balances`, verified by `dgway:inventory:verify`
(both projections against the ledger) and rebuildable by
`dgway:inventory:rebuild-balances`. Invariant: Σ lot balances of a position =
the position balance.

## 9. Relationship with the ledger (impact analysis on StockKey)

`StockKey` (product × node × bucket) was **kept unchanged**. Making the lot part
of the key would have changed every balance row, every lock and every A3/A4
query and test; the lot is instead an extra column on the movement and a
second, finer projection. Consequences:

- position balances, negative-stock policy and position locks behave exactly as in A3/A4;
- every movement written after the A5-B cut-over MUST name a lot
  (`sm_lot_required_check`: `lot_id IS NOT NULL OR created_at < dgway_lot_cutover()`);
- movements written before stay `lot_id NULL` forever (append-only) and belong
  to `dgway_legacy_lot(product, node)`; they are consumed first (oldest).

## 10. Concurrency

Lock order (same everywhere, deadlock-free):

1. document rows (sale / receipt) as in A4;
2. customer credit row (credit sales) as in A4;
3. **stock positions** in StockKey order (`stock_balances` FOR UPDATE);
4. **lot balance rows of those positions** (`stock_lot_balances … FOR UPDATE OF b`, FIFO order) — the allocator reads them only after holding (3);
5. StockPosting locks the touched lot balances in `LotBalanceKey` order, applies, saves.

Because (3) serialises every consumer of a position, a second sale waits and
then sees the first one's consumption: "Lot A remaining 50, two concurrent
40 kg sales" gives A→40 to the first and A→10 + B→30 to the second (or
INSUFFICIENT_STOCK when B does not exist) — proven with separate OS processes
in `LotMultiProcessTest`. `stock_lot_balances` has `CHECK (quantity >= 0)`.

## 11. Read API and traceability

`GET /lots`, `/lots/{id|number}`, `/lots/{id}/movements`, `/lineage`,
`/destinations`, `GET /inventory/lot-balances` (API_CONTRACT_V1.md), all
paginated, constant query count. `php artisan dgway:trace LOT-261003-001`
prints LOT → PRODUCT → SUPPLIER → GR → DISPOSITIONS → LINEAGE → MOVEMENTS →
SALES → CUSTOMERS → AUDIT.

## 12. Project B evolution

- The lot UUID is the stable identity a marketplace/fulfilment platform can
  reference (order → shipment → lot) without renumbering.
- Multi-node: lots are already per node; a future TRANSFER_OUT/IN would move a
  lot between nodes keeping its id (the movement types exist, not used yet).
- FEFO / expiry, quality holds and recalls are allocation/status policies on
  top of this model (recall = `GET /lots/{id}/destinations`).
- Unit-level serialisation (per tray/egg) is NOT in this model; it would be a
  child entity of a lot.

## 13. DG Way lot ≠ supplier batch; collection date ≠ received date (A5-C)

An InventoryLot is **DG Way's internal lot**: what DG Way received in one
receipt line. It is not a supplier production batch, and its number
(`LOT-YYMMDD-NNN`, dated by the DG Way receipt) must never be read as one.

Optional upstream facts, recorded on the goods-receipt line and copied to the lot at posting:

| Field | Meaning | Unknown |
| --- | --- | --- |
| `collection_date` | the date the supplier/farm states the goods were collected (eggs: collected/separated). Not a production/laying date. | `NULL` |
| `supplier_reference` | the supplier's own batch/reference text, only if the supplier really gives one (≤ 60 chars) | `NULL` |
| `manufactured_date`, `best_before_date` (A5-B) | only when genuinely stated | `NULL` |
| `business_date` / `received_at` | when **DG Way received** the goods (always known) | — |

Supplier situations:
- **A — agent/distributor**: nothing known upstream → all upstream facts `NULL`; DG Way still creates its lot.
- **B — direct farm with separated collection** (collected 2026-10-04, received 2026-10-05): `collection_date = 2026-10-04`,
  `business_date = 2026-10-05`, `supplier_reference = NULL` — the collection date is not turned into a batch number.
- **C — supplier with its own reference**: `supplier_reference` stores it, distinct from the DG Way lot identity.

Validation (exact rule): `collection_date` is optional; when given it must be a valid date,
**≤ the receipt business date** (cannot be collected after DG Way received it) and **≥ `manufactured_date`**
when both are given → otherwise `COLLECTION_DATE_INVALID`. No minimum age (eggs held at the farm are normal).
It is never defaulted from the receipt date, `received_at`, `created_at` or any movement date.

Lineage: a REGRADE lot inherits the parent's upstream facts (same goods). ADJUSTMENT and LEGACY lots never carry
upstream facts (CHECK `lot_upstream_check`). The database refuses a lot whose upstream facts differ from its receipt
line or parent (`dgway_lot_guard`, `LOT_UPSTREAM_MISMATCH`). Lots are append-only, so the facts cannot be edited later.

Migration `2026_10_05_100100_add_lot_upstream_facts` added the columns empty: existing lots keep `NULL`
(evidence: `docs/evidence/a5c-migration-roundtrip.txt`). Read models, `dgway:trace` and the lot label show
"Diterima DG Way" and "Tanggal Pengumpulan" as two separate facts; an unknown collection date is omitted.
