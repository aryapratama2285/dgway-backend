# Data Evolution Strategy — Project A → Project B

> **DG Way Core Transactional Data — Generation 1.**
> Project A is not a disposable prototype. Its database and transaction
> history are the first generation of the DG Way platform's data. Project B
> must be able to grow from it without losing history or identity.

Companion artefacts (all kept in sync by tests):

| Artefact | What it is |
| --- | --- |
| `config/data_contract.php` | machine-readable contract: owner context, aggregate, kind, migration class, business key, semantic fingerprint columns — for **every** table |
| `docs/SCHEMA_CATALOG.md` | generated from the live database + contract (`php artisan dgway:schema:catalog`); the suite fails if it is stale |
| `php artisan dgway:data:fingerprint` | reconciliation: economic invariants + strong per-table checksums; `--compare` before/after a migration |
| `php artisan dgway:trace <number-or-uuid>` | follows a transaction through documents, ledger, money, actors and audit |
| `tests/Feature/DataEvolution/*` | prove the contract matches the database and the guarantees hold |

---

## 1. Stable identity

**Rule:** every business record has a UUID primary key generated by the
application (UUIDv7: time-ordered, globally unique). No identity depends on a
database sequence, an auto-increment, a Laravel model or a server, so it does
not need to be recreated when the backend changes and records from several
systems/nodes can be merged without collisions. The contract test asserts
this for every preserved table: PK = `id`, type `uuid`, no database default.

| Entity | Table | Identity | Business key | Guarantee |
| --- | --- | --- | --- | --- |
| Product | `products` | `id` | `sku` (immutable) | DB: never deleted, `id`/`sku` immutable (`dgway_guard_identity`) |
| Category | `product_categories` | `id` | `code` | same |
| Unit of measure | `uoms` | `id` | `code` (referenced by FK from lines/ledger) | same |
| Business partner | `business_partners` | `id` | `code` | same |
| Supplier / customer role | `business_partner_roles` | `id` | `(partner_id, role)` UNIQUE | same (role row never deleted, its partner/role never changes) |
| Location | `locations` | `id` | `code` | same |
| Node | `nodes` | `id` | `code` (e.g. `DG-WAY-PRIMARY`) | same |
| Operator (actor) | `users` | `id` | `email` | never deleted, `id` immutable |
| Purchase order | `purchase_orders` (+lines) | `id` | `number` `PO-YYMMDD-NNN` UNIQUE | never deleted; terms immutable |
| Goods receipt | `goods_receipts` (+lines, dispositions) | `id` | `number` `GR-…` | immutable once POSTED; reversal instead of edit |
| Stock movement | `stock_movements` | `id` | — (`sequence` = global order, `correlation_id` = posting) | append-only |
| Inventory operation | `inventory_operations` | `id` | `number` `INV-…` | append-only |
| Sale | `sales` (+lines) | `id` | `number` `SAL-…` | immutable once confirmed; returns / reversal instead of edit |
| Payment | `payments` | `id` | `number` `PAY-…` | append-only; `payment_reversals` (UNIQUE per payment) |
| Customer return | `customer_returns` (+lines) | `id` | `number` `RET-…` | append-only |
| Audit / event reference | `audit_logs` | `id` | `(entity_type, entity_id)` + `context` | append-only |

Notes:
- `stock_movements.sequence` is **ordering, not identity**. A migration copies
  its values; it must never renumber them.
- Document numbers are unique per table and must never be reissued, so
  `document_sequences` is **carried over** (not rebuilt from zero).
- Since A5 the database itself rejects deleting a master record or changing
  its UUID/business key, even for unreferenced rows and raw SQL
  (migration `2026_10_03_400100_guard_master_data_identity`, test
  `StableIdentityTest`, which failed before the guard existed).

## 2. Historical continuity

Project B may split today's modules into more contexts. The history moves
with its identity; it is never thrown away because a boundary moved.

| Project A (Generation 1) | Likely Project B home | Continuity rule |
| --- | --- | --- |
| Purchase order, goods receipt, dispositions | Procurement / Commerce (buy side) | same ids and numbers; B references `goods_receipts.id` |
| Stock movements, inventory operations, balances | Inventory | ledger rows copied 1:1 (see §5); balances rebuilt |
| Sale, sale lines, customer returns | Commerce / Order-to-cash | same ids; future customer orders reference `sales.id` via `order_reference_id` |
| Payments, payment reversals | Payment / Settlement | append-only history copied 1:1 (see §6) |
| Receivable (derived) | Receivables / Credit | recomputed from preserved sales, payments, returns — never imported as a typed-in balance |
| Audit logs | Audit / Event history | copied 1:1; B's own audit starts after it, same `entity_id` space |
| Catalog, partners, network | Master data / Marketplace catalog | same ids; B adds attributes, never re-keys |

## 3. No destructive migration by default

- **Forward-only in production.** `DB::prohibitDestructiveCommands()` is on in
  production (`AppServiceProvider`): `migrate:fresh`, `migrate:refresh`,
  `migrate:reset`, `migrate:rollback` and `db:wipe` refuse to run (test
  `NoDestructiveMigrationTest`). `down()` methods exist for development only;
  several of them drop tables and must never touch production data.
- **Expand → migrate → contract.** A breaking change is three releases:
  (1) add the new column/table alongside the old, (2) backfill
  deterministically and switch reads/writes, (3) remove the old structure only
  after a reconciliation sign-off and a retention period.
- **Gate every data migration** with `dgway:data:fingerprint --output` before
  and `--compare` after (§7), plus a `pg_dump` backup.
- The forbidden strategy: *DROP old data → create new system → start from
  zero.* An opening-balance cut-over is allowed only as an addition (an
  explicit opening movement whose source is the archived Generation-1
  ledger), never as a replacement of the history.

## 4. Bounded-context data ownership

One writer per table. Other contexts read, or reference by id; they never
keep a second copy of the truth.

| Context | Owns (single source of truth) | Others may | Must NOT be duplicated as |
| --- | --- | --- | --- |
| Identity | `users` (actors) | reference `actor_user_id` | a second user table with other ids |
| Catalog | `products`, `product_categories`, `uoms` | reference `product_id`, `uom_code` | product copies inside sales/inventory |
| Partner | `business_partners`, `business_partner_roles` (terms, credit limit) | reference `customer_id` / `supplier_id`; Sales reads terms at confirmation | a customer table owned by Sales |
| Network | `locations`, `nodes` (capabilities) | reference `node_id` | warehouse lists per module |
| Procurement | `purchase_orders`, `goods_receipts` (+lines, dispositions): what was ordered, received, at what **cost** | read cost/yield for analytics | cost fields on inventory or sales tables |
| Inventory | `stock_movements` (truth), `inventory_operations`; `stock_balances` = projection | read balances; post movements only through the ledger | any "stock quantity" column elsewhere |
| Sales | `sales`, `sale_lines` (transaction **price** snapshot), `customer_returns` | read revenue | a product "sale price" treated as history |
| Payment / Receivable | `payments`, `payment_reversals`; receivable = derived from sales + payments + returns | read outstanding | a typed-in receivable balance |
| Shared | `audit_logs`, `document_sequences`, `idempotency_keys` | — | — |

In Generation 1, Payment/Receivable code lives in the Sales module
(`App\Domain\Sales`); the contract already lists `payments` /
`payment_reversals` under the Payment context so Project B can extract it
without re-deciding ownership.

## 5. Ledger continuity

The inventory ledger is copied, never re-shaped:

1. Copy every `stock_movements` row 1:1: same `id`, `sequence`,
   `movement_type`, `direction`, `quantity`, `bucket`, `business_date`,
   `occurred_at`, `source_document_type/id/line_id`, `correlation_id`,
   `reverses_movement_id`, `actor_user_id`, `reason`, `unit_cost`.
2. Semantic contract: quantity is a positive magnitude in the product's base
   UOM, `direction` ±1, `signed_quantity = quantity × direction`; REVERSAL
   rows mirror the movement they reverse. New movement types in B are
   additions (extend the CHECK); old rows keep their type.
3. Rebuild `stock_balances` from the ledger (`dgway:inventory:rebuild-balances`)
   instead of importing it.
4. Verify deterministically: `stock_by_position` (Σ signed per
   product/node/bucket) and `stock_movements_by_type` invariants plus the
   row-level checksum (§7).

A migration may **add** columns (e.g. lot, location bin) with defaults; it may
not update historical rows to fit a new model. A5-B did exactly this for lots
(§13): `stock_movements.lot_id` was added, historical rows keep `lot_id NULL`
and are attributed to a documented LEGACY lot — no history was rewritten.

## 6. Financial history continuity

Economic meaning in Generation 1 (must survive any migration unchanged):

| Concept | Meaning |
| --- | --- |
| valid payment | a `payments` row without a `payment_reversals` row |
| reversed payment | both rows exist; the payment row is never altered or deleted |
| credit (return) | `customer_returns.credit_amount` reduces what is owed |
| refund | `customer_returns.refund_amount` = money given back (`refund_method`) |
| outstanding | `grand_total − Σ valid payments − Σ credits` for CONFIRMED/COMPLETED sales; 0 otherwise; never negative |
| money | IDR, `NUMERIC(19,4)`, half-up to 4 dp (Generation-1 rounding policy) |

Migration rules: never net payments into one amount, never turn a reversal
into a deletion, never recompute historical totals with a new rounding rule
(a new rule applies to new documents only), never import outstanding as a
typed number. `sales.paid_amount` / `credited_amount` are cached sums that a
deferred database trigger re-checks against the payment and return history
at every commit.

## 7. Migration reconciliation

`php artisan dgway:data:fingerprint` emits deterministic JSON:

**Invariants (economic meaning)**

| Invariant | Old = migrated |
| --- | --- |
| sales count and Σ grand total per status | yes |
| open sales, Σ outstanding, and outstanding recomputed from components | yes, both equal |
| outstanding per customer | yes |
| payments: count, gross, reversed count/sum, Σ valid; Σ valid per method | yes |
| customer returns: count, Σ value, Σ credit, Σ refund | yes |
| ledger: count and Σ signed per movement type; Σ signed per product/node/bucket | yes |
| goods receipts: count and Σ cost per status; purchase orders per status | yes |
| document sequences: last date and issued count per prefix | yes |
| audit: count and last timestamp | yes |
| lots (A5-B): count/original per origin; Σ original = Σ creating movements; remaining per origin × bucket and per lot (md5); movements per type with legacy attribution; unattributed movement count; lineage edges (md5) | yes |

**Strong check:** for every `preserve` table, row count +
`md5(string_agg(semantic columns, ORDER BY id))`. Any changed value, missing
row, extra row or changed id changes the hash. Generated/derived columns are
excluded and covered by the invariants.

**Procedure:**
1. Freeze writes (maintenance mode).
2. `pg_dump`, then `dgway:data:fingerprint --output=before.json`.
3. Run the migration.
4. Rebuild projections (`dgway:inventory:rebuild-balances`).
5. Run `dgway:data:fingerprint --compare=before.json`. Exit 0 means OK; on
   exit 1, roll forward a fix or restore.
6. Spot-check a few transactions with `dgway:trace`. A target outside this
   codebase reproduces the same SQL projections.

**Normalized comparison (A5-B).** `--compare` keys list-shaped sections by
their natural key (status, prefix, movement type, product/node/bucket …)
before diffing, so a NEW row (e.g. the `LOT` document prefix) is reported as
one addition instead of shifting every later index. `--allow-additions`
accepts keys that did not exist in the older fingerprint (new tables, new
columns hashed separately as `"<table>+added"` via `fingerprint_added` in the
data contract, new invariant sections) while still failing on any changed or
missing value. The JSON format is unchanged, so older baselines stay comparable.

Proven by `MigrationToolingTest`: a business change is reported, and a
history rewrite by a "migration" (trigger disabled inside a transaction) is
detected by the checksum even when quantities are untouched. Evidence on the
dev database (rollback + re-migrate of a schema change → fingerprint
identical): `docs/evidence/a5-data-evolution-reconciliation.txt`.

## 8. Technology independence

The data contract is the **PostgreSQL schema**, not the PHP code:
- UUID keys, `NUMERIC` money and quantities (decimal strings in the API),
  `DATE` business dates, `TIMESTAMPTZ` instants, enumerations as text +
  CHECK, JSON only for audit snapshots.
- The critical invariants are enforced in the database (CHECKs, append-only
  triggers, status/immutability guards, deferred money check, ledger reversal
  mirror). A Java service, another backend or a data tool writing to these
  tables is held to the same rules.
- Laravel-specific tables (`migrations`, `cache*`, `jobs*`, `failed_jobs`,
  `personal_access_tokens`) are classified `discard` in the contract.
- Append-only ledgers with a global `sequence` are natural sources for change
  data capture or an analytics platform: read new rows after the last
  sequence; never mutate.
- Accepted coupling: PL/pgSQL triggers bind the data to PostgreSQL, not to a
  framework.
- No polyglot or microservices in A5 — only a clear semantic contract.

## 9. Migration path, not a big-bang rewrite

```
Project A modular monolith (contexts already separated in code and data ownership)
        ↓  add contexts / features inside the same deployable (orders, delivery, pricing …)
Larger modular platform (same database, more contexts, outbox for integration)
        ↓  only when justified: independent scaling, team ownership, regulation
Selective extraction of one context (its tables move with their ids; cross-context
FKs become id references + events)
```

The tables that would move together are already grouped by owner in the
contract, and the cross-context foreign keys an extraction must replace are
listed in `docs/SCHEMA_CATALOG.md`.

## 10. Programmer traceability

```
business transaction  → document (number + UUID)        sales / goods_receipts / payments / customer_returns / inventory_operations
  → domain entity      → lines                          sale_lines, goods_receipt_lines, customer_return_lines …
  → consequence        → stock_movements                source_document_type/id/line_id; correlation_id = posting
                       → payments / payment_reversals / customer_returns   (sale_id)
  → actor              → users.id                       actor_user_id / created_by / posted_by / confirmed_by / reversed_by
  → audit              → audit_logs                     entity_type + entity_id, before/after, context (document number, reason, idempotency key)
  → reference ids      → correlation_id (one per posting: GR id, sale id, return id, INV id; a reversal gets a new one)
                         reverses_movement_id (reversal → original), order_reference_id (future orders)
```

`php artisan dgway:trace SAL-261003-002` (or any document number, document /
payment / movement / correlation UUID; `--json` for tooling) prints all of
it. Example output: `docs/evidence/a5-data-evolution-reconciliation.txt` §6.

## 11. Schema documentation

- **Table ownership and aggregate ownership:** `config/data_contract.php` →
  `docs/SCHEMA_CATALOG.md` (Tables section).
- **Immutable tables:** kind `append_only` (`stock_movements`,
  `inventory_operations`, `payments`, `payment_reversals`,
  `customer_returns(+lines)`, `audit_logs`). Kind `document` / `line` become
  immutable when final (`dgway_goods_receipt_guard`, `dgway_sale_guard`,
  `dgway_sale_line_guard`, `dgway_receipt_detail_guard`, `dgway_po_line_guard`).
  Kind `master` is never deleted and keeps its identity.
- **Generated / derived values:**
  - `stock_movements.signed_quantity` (generated column);
  - `sales.outstanding` (generated column);
  - `stock_balances` (projection, rebuild);
  - `sales.paid_amount` / `credited_amount` and `sale_lines.returned_*`
    (cached sums, verified at commit).
- **Critical constraints, triggers, indexes, FKs:** per table in
  `docs/SCHEMA_CATALOG.md`; meaning in `DATABASE.md`,
  `docs/INVENTORY_LEDGER.md`, `docs/SALES_AND_RECEIVABLES.md`.
- **Cross-context references:** generated table in `docs/SCHEMA_CATALOG.md`.
- **Guard rails:** `DataContractTest` fails when a table is added without a
  contract entry, when a declared guarantee is missing in the database, or
  when the catalog document is stale.

## 12. Project B readiness assessment

**Usable directly by Project B**
- Master data identities (products, partners/roles, nodes, UOM), UUIDv7
  everywhere, immutable business keys.
- The inventory ledger with movement types, buckets, reversal semantics and a
  rebuildable projection.
- Procurement history with raw cost and yield.
- Sales with price snapshots, append-only payments/reversals/returns and
  derived receivables.
- Audit trail, document numbering, idempotency pattern, and the
  reconciliation/trace tooling.

**Likely to be extended**
- Customer orders / fulfillment (`sales.origin = ORDER`, `order_reference_id`
  already present).
- Pricing (price lists), expiry/FEFO policy on top of lots, more buckets,
  transfers between nodes (types already declared).
- UOM conversions / pack sizes.
- Delivery.
- Multi-company / organisation dimension.
- COGS valuation computed from preserved history.

**May one day be separated**
Payment/Settlement (already its own aggregate and tables), Inventory,
Procurement, Catalog/marketplace. Extraction moves tables with their ids and
replaces cross-context FKs with id references + events.

**Data that must be preserved (`migration = preserve`)**
- Every master table.
- PO, GR (+lines, dispositions).
- `stock_movements`, `inventory_operations`, `inventory_lots` (A5-B).
- `sales`, `sale_lines`, `customer_returns(+lines)`.
- `payments`, `payment_reversals`, `audit_logs`.
- Plus `document_sequences` (carry over).

Rebuildable: `stock_balances`, `stock_lot_balances`. Discardable: framework tables, tokens,
idempotency keys after retention.

**Technical debt that could hinder migration**
1. **No outbox / event stream:** `audit_logs` is an audit trail, not an
   integration event log. Extraction will need an outbox or CDC on the
   ledgers.
2. **No organisation/tenant dimension:** a marketplace or multi-company
   Project B must add one (expand migration with a default organisation for
   all Generation-1 rows).
3. **Payment/Receivable code lives in the Sales module:** ownership is
   declared, the code split is not done.
4. **Free-text type columns:** `source_document_type` and
   `audit_logs.entity_type` are free text, only format-checked. A registry or
   CHECK list would make cross-system joins safer.
5. **PO header status machine is enforced only in the domain:** the database
   blocks only deletes and line-term changes, unlike GR and sales.
6. **Document numbering assumes one numbering space:** `PREFIX-YYMMDD-NNN`
   per prefix. Multi-entity numbering needs an entity component in the prefix.
7. **Single currency (IDR) is a default in code:** columns carry `currency`,
   but there is no FX.
8. **Two clocks:** `created_at` uses database time (`now()`), while
   `occurred_at` / `business_date` come from the application clock. This is
   documented; B must keep both and not "fix" one from the other.
9. **The Generation-1 rounding policy is implicit:** half-up, 4 dp, not stored
   per document. It is documented here; a future policy change must be
   recorded per document.
10. **Walk-in sales use `customer_id = NULL`:** B may want an explicit
    anonymous party.
11. **`users` is Laravel-shaped:** password and remember_token columns. If
    identity moves to an external identity provider, keep `users.id` as the
    stable actor id.
12. **`nodes.capabilities` is a PostgreSQL text array:** fine for PostgreSQL;
    another store needs a mapping.
13. **`down()` migrations of A3/A4 drop tables:** development only. This is
    prohibited in production but should not be relied upon outside it either.

## 13. A5-B — lots as a ledger dimension (Generation 1, revision 2)

**What changed (expand-only).**

| Object | Kind | Migration class |
| --- | --- | --- |
| `inventory_lots` | new append-only table (identity + provenance) | preserve |
| `stock_movements.lot_id` | new nullable FK column (+ index `lot_id, sequence`) | preserve (`fingerprint_added`) |
| `stock_lot_balances` | new projection (lot × node × bucket) | rebuild |
| `goods_receipt_lines.manufactured_date`, `best_before_date` | new optional columns | preserve (`fingerprint_added`) |
| functions/triggers | `dgway_legacy_lot`, `dgway_lot_cutover`, `dgway_lot_guard`, `dgway_movement_lot_guard`, deferred `dgway_check_lot_origin_quantity`, lot clause in `dgway_validate_reversal` | — |

**Historical rows are not rewritten.** Movements written before the cut-over
keep `lot_id NULL` (CHECK `sm_lot_required_check`: `lot_id IS NOT NULL OR
created_at < dgway_lot_cutover()`). The migration creates ONE `LEGACY` lot per
product × node that had history, with `original_quantity NULL`, no supplier and
no receipt (`provenance = UNATTRIBUTED_LEGACY` in the API). Supplier/lot facts
that were never recorded are **not invented**. `dgway_legacy_lot(product, node)`
resolves a NULL `lot_id` wherever lots are computed (projection rebuild,
verify, fingerprint, reversal of an old movement).

**Deterministic legacy identity.** The legacy lot id is derived from
md5(product, node) and its number is dated at the first known movement, so a
development rollback + re-migrate reproduces the same lots (strict fingerprint
equality, `docs/evidence/a5b-migration-roundtrip.txt`,
`LotReconciliationTest::test_rollback_and_remigrate_over_pre_a5b_history_reconcile`).

**Evidence (development database with A4 history):** strict compare of the
rolled-back database = identical to the pre-A5-B baseline; after up,
`--allow-additions` = identical (additions: `document_sequences.LOT`, `lots`,
`inventory_lots`, `stock_movements+added`, `goods_receipt_lines+added`);
`stock_by_position` and `stock_movements_by_type` unchanged; `inventory:verify`
consistent (both projections).

**Rollback caveat.** `down()` drops the lot column and tables: after real
post-cut-over activity it would lose lot attribution (stock quantities stay
correct). It is a development tool; production never rolls back
(DEPLOYMENT.md §5).

**Project B.** Lot ids are stable references for orders, shipments and recalls;
FEFO/expiry and transfers are policies/movements on top of the same model
(BATCH_LOT_MODEL.md §12). Technical debt added: `stock_lot_balances` uses
`lot_id` without a tenant/organisation dimension (same as every other table, §12 item 2).

## 14. A5-C — upstream lot facts and print settings (Generation 1, revision 3)

| Object | Kind | Migration class |
| --- | --- | --- |
| `goods_receipt_lines.collection_date`, `supplier_reference` | new nullable columns | preserve (`fingerprint_additions.a5c` → checksum `goods_receipt_lines+a5c`) |
| `inventory_lots.collection_date`, `supplier_reference` | new nullable columns | preserve (`inventory_lots+a5c`) |
| `print_settings` | new single-row configuration table (business identity, receipt width) | preserve |
| `dgway_lot_guard` | extended: lot upstream facts = receipt line / parent | — |

- No backfill: unknown upstream facts stay `NULL` (historical uncertainty explicit).
- New fingerprint invariant `lots.upstream` (per origin: lots with collection date / supplier reference + md5).
- Per-phase checksum groups (`fingerprint_additions`) keep the A5-B `"+added"` checksums byte-identical.
- Evidence (`docs/evidence/a5c-migration-roundtrip.txt`), on the A4-history dev DB and on the A5-B smoke DB:
  up → `--allow-additions` identical (additions only); existing lots/lines with collection date = 0;
  verify OK; down → strict identical; re-up → strict identical; verify OK.
